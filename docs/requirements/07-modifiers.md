## 1. Model & Constants

- `modifiers: Array<{id, type:'amplify'|'nullify'|'flip'|'rotate', x, y, radius:number, isDragging?:boolean}>` in `src/main.js` (or exported via `src/vectorField.js:setModifiers`). Spatial modifiers are `amplify`/`nullify`/`flip`/`rotate`; `freeShot` is **not** a spatial modifier and is never pushed to `modifiers` (it is a passive attempt stock).
- `supply = { amplify:number, nullify:number, flip:number, rotate:number, freeShot:number }` in `src/main.js` (or `src/supply.js`). `rotate` is spatial (90° CCW), `freeShot` is a consumable attempt modifier, not a field circle.
- `isFreeShotActive:boolean` (or `isFreeShotArmed` / `freeShotActive`) in `src/main.js` — whether the next launch will be a free shot. It is **no longer toggled manually** (no hotkey); it is only auto-armed when `getAttemptsLeft()<=1 && supply.freeShot>0` at launch init (see §5.2). Toggling does not create a circle and does not call `syncModifiersToField` for a spatial entry. `rotate` has no active toggle.
- Base constant `BASE_MODIFIER_RADIUS` normative: latest spec uses `54` (reduced 40% from `90`; see `09-rewards-and-progression.md` for upgrade math). Earlier `90` is legacy and **superseded by `54`** per clarification (later requirement wins). Define once: `BASE_MODIFIER_RADIUS=54` or `90`→`54` at top of `src/main.js`/`src/vectorField.js`; document chosen value. Effective radius is `getEffectiveModifierRadius()` (see §4). Applies to spatial types (`amplify`/`nullify`/`flip`/`rotate`); `freeShot` has no radius.
- `MODIFIER_RADIUS` is not mutated directly; effective radius is derived via multiplier.

## 3. Placement Interaction `src/input.js` + `src/main.js`

- **Spatial modifiers (`amplify`/`nullify`/`flip`/`rotate`)**: Preview circle dashed `50%` of effective radius, color per type, following mouse via `getCanvasMousePos` when a spatial modifier is selected and state is `AIMING`/`CHARGING`; no preview when `null` or supply insufficient (or desaturated red).
  - Left-click places at cursor's logical coords if `canPlace(selectedModifier)` (see §6) and not overlapping `FLYING`; after placement `selectedModifier=null` (must re-select for next). Placing does not launch.
  - **Dragging**: `mousedown` on existing circle (`dist<radius`) enters dragging, `mousemove` updates `x,y`, `mouseup` finalizes; works only before shooting; dragged opacity `0.6`, `grabbing` cursor; does not delete or consume supply.
  - Right-click or `Delete`/`Backspace` on a circle removes it (frees supply slot, see §6); dragging does not delete. `R` ball reset does NOT clear modifiers; advancing hole or game reset does (see §7).
- **Free Shot — passive stock (no placement, no hotkey)**: `Free Shot` is **not** placed as a circle and has **no hotkey**; it is not selectable via `1-4` and has no preview. Its supply is shown in the HUD after `Attempts Left` (e.g. `Attempts Left: 5 (+5)`) and is consumed automatically via auto-arm (see §5.2). `isFreeShotActive` is only set by auto-arm (`getAttemptsLeft()<=1 && supply.freeShot>0` at launch init), never by manual `4`. Visual feedback for Free Shot active is still the golden glowing effect over the ball in the Three.js layer (see §5.2), but there is no hotbar slot for it.
- **Rotate (`4`) — spatial 90° CCW**: Selecting `rotate` via `4` or hotbar Slot 4 shows preview circle `50%` effective radius, red `rgba(231,76,60,0.25)` ring `↻` (see §5.1). Placement/drag/removal same as other spatial modifiers.

## 4. Effective Area (Area Upgrades)

- State `areaUpgradeCount >=0` (`0` on new game) defined in `09-rewards-and-progression.md` but **applied here**. Multiplier `areaMultiplier = 1 + 0.2*areaUpgradeCount` (**additive**, not `1.2^n`; two gives `1.4` → e.g. `54*1.4=75.6`, not `77.76`).
- `getEffectiveModifierRadius() = BASE_MODIFIER_RADIUS * areaMultiplier` (e.g. `54,64.8,75.6,86.4...`; or `90,108,126,144` if base were 90 — use actual base). Applies to spatial modifiers (`amplify`/`nullify`/`flip`/`rotate`).
- All hit tests (`getWindAt`, dragging, preview, removal) shall use effective radius. Existing modifiers grow retroactively on `Area Up` acquisition (either update each `m.radius` or compute lazily via getter).
- `freeShot` has no radius and is unaffected by `areaMultiplier`; `rotate` uses same effective radius as other spatial modifiers.

## 5. Per-Type Effects

### 5.1 Spatial Wind Effects (applied in `getWindAt` after base field + bilinear, placement order for presence but rotation magnitude deduped)

- **Amplify (`factor 5` per circle)**: `if type==='amplify' && inside → wind*=5` multiplicative. Stacking: one→`5×`, two→`25×`, three→`125×` (no hard cap; practical supply limits to `25×` with starting supply, further rewards allow `125×`). Capped handling previously at `25×` is superseded.
- **Nullify (`factor 0`)**: `getWindAt` returns `{0,0}` for visualization (faint); **physics inside nullify (see `04-physics-and-collision.md`) skips both wind and friction** so ball keeps entry velocity (`isInsideNullify` branch). Stacking: nullify dominates (over amplify/flip/rotate, result `{0,0}` and preserved velocity). Minimum-force rule is intentionally violated inside nullify for physics but visualization shows zero.
- **Flip (`factor -5` includes one amplify)**: `if type==='flip' && inside → wind = (-wind) *5` (flips 180° and increases strength 5×, same as one amplifier). **Stacked flips/rotates deduped**: any number of `flip`+`rotate` circles combined contribute **exactly one** `5×` factor regardless of count (e.g. two flips → `5×` identity direction, not `25×`; `flip+rotate` → `5×` 270°, not `25×`). Further amplified by explicit `amplify` circles: `amplify(5)+flip(-5)` → `-25×` (`5×5` flipped), `amplify+rotate+flip` → `25×` 270°, `2×amplify+rotate` → `125×` 90°, etc. Magnitude is `5 ** (amplifyCount + (flipCount+rotateCount>0?1:0))`.
- **Rotate (`90° CCW` includes one amplify)**: `if type==='rotate' && inside → wind = rotate90CCW(wind) *5` where `rotate90CCW(x,y) = (-y, x)` (counter-clockwise) **and** strength 5× like `amplify`. Applied as deduped group with `flip`: any number of `rotate`+`flip` together give exactly one `5×` (e.g. one rotate → `5×` 90° CCW, two rotates → `5×` 180°, three → `5×` 270° CCW, four → `5×` 360° identity `5×` not `1×`). Multiple rotates stack angle `rotateCount*90° CCW` plus flips `flipCount*180°` modulo 360°, but magnitude from the group stays `5×` once. Explicit `amplify` circles further amplify: `amplify(5)+rotate(5×90° CCW)` → `25×` 90° CCW, `2×amplify+rotate+flip` → `125×` 270° CCW, etc. Nullify still dominates (if nullify present, result `{0,0}` regardless of rotate/flip).
- Circular area: `dist < effectiveRadius` where `effectiveRadius = getEffectiveModifierRadius()`. Performance `O(n)` where `n`=modifiers length.
- **Normative formula**: `amplifyCount = |{m:inside ∧ type==='amplify'}|`, `flipCount = |{m:inside ∧ type==='flip'}|`, `rotateCount = |{m:inside ∧ type==='rotate'}|`, `hasRotFlip = (flipCount+rotateCount)>0`, `totalFactor = 5**(amplifyCount + (hasRotFlip?1:0))`, `totalQuarterTurns = (rotateCount + 2*flipCount) %4`, `wind = (base * totalFactor) rotated totalQuarterTurns*90° CCW` (`(-y,x)` per quarter). Nullify dominates first.

Visualization on `game` canvas (below wind overlay):
- `amplify` solid orange `rgba(230,126,34,0.25)` ring `»` with white icon, `nullify` blue dashed `rgba(52,152,219,0.25)` `∅` white icon, `flip` purple `rgba(155,89,182,0.25)` `⇄` white icon, `rotate` red `rgba(231,76,60,0.25)` ring `↻` with **red icon `↻` `#e74c3c`** (refresh, distinct color `#e74c3c`, alternative `#c0392b`/`#ff6b6b` acceptable, not orange/blue/purple/gold). Dragged at 60% opacity. Ghost trails / arrows inside any modifier show amplified speed: `amplify`/`flip`/`rotate` all `5×` faster (flip reversed, rotate 90° CCW), `nullify` stalls.

### 5.2 Free Shot — Consumable Attempt Modifier (non-spatial, passive, no hotkey)

- **Effect**: When `isFreeShotActive === true` and a launch is performed (`handleLaunch` / `launchBall`), that **attempt does not decrease `Attempts Left`**: `holeAttempts`/`totalAttempts` are **not** incremented for that launch, and `attemptsLeft = maxAttempts - holeAttempts` is unchanged. The ball still launches with normal physics (`power`/`angle` unchanged). `isFreeShotActive` is **not** a wind effect and does not enter `getWindAt`. Free Shot has **no hotkey** and is **not shown in the modifier bar**; its supply is shown in the HUD as `Attempts Left: X (+Y)` where `Y = supply.freeShot` (e.g. `Attempts Left: 5 (+5)`), see `03-rendering.md`.
- **Consumption & Persistence**: After a launch that was free (i.e. `isFreeShotActive` was true at launch time and `supply.freeShot > 0`), do `supply.freeShot = max(0, supply.freeShot - 1); if (supply.freeShot > 0) keep `isFreeShotActive=true` (persist armed) else `isFreeShotActive=false`; `updateHotbarUI(); saveProgress();`. Consumed exactly once per free launch but **persists while supply remains** so consecutive free launches do not require manual activation. If `isFreeShotActive` was false, normal cost applies and `supply.freeShot` is untouched. **Auto-arm only** (see `05` §4): if at launch initialization `!isFreeShotActive && supply.freeShot>0 && getAttemptsLeft()<=1`, automatically set `isFreeShotActive=true` before branching so the last attempt becomes free. There is **no manual toggle via `4`** (4 is now `rotate`).
- **Visual feedback — golden glowing effect over ball in Three.js layer + subtle edge glow**: **Ball glow** is shown **only while `isFreeShotActive===true` (armed before launch)** and is **removed immediately after launch** (even though `freeShotFlightActive` remains true, ball glow is hidden during flight); **Edge glow** is shown **while `isFreeShotActive===true` OR while `freeShotFlightActive===true` (through `FLYING` until ball stops, resets, or wins)**. The Three.js overlay (`#wind-canvas`, `src/windThree.js`) renders a **golden glowing effect centered on `ball.pos`** above the ball when armed. Implementation may be a `THREE.Sprite`/`Mesh`/`Point` with `additive` blending, `color 0xf1c40f` / `0xFFD700`, `opacity 0.55-0.85`, `radius 14-22px` logical (scaled by DPR), soft falloff, pulsation `scale 1.0 + 0.15*sin(time*3)` and `opacity` flicker. Must be in `windThree.js` on `#wind-canvas` (z-index 3-4) so it appears over ball but below HTML overlays; must use `pointer-events:none`, `depthWrite:false`, `transparent:true`. **Edge glow** (`div#free-shot-edge-glow` `position:absolute; inset:0; border-radius:8px; border:2px solid rgba(241,196,15,0.38); box-shadow: inset 0 0 36px rgba(241,196,15,0.22), inset 0 0 70px rgba(241,196,15,0.12), 0 0 18px rgba(241,196,15,0.28); opacity 1 when edge active else 0, transition 220-260ms, z-index:4, pointer-events:none`) **persists through flight** while ball glow is hidden. Canvas 2D fallback (if Three not ready) may draw gold ring `rgba(241,196,15,0.45)` `stroke 2px` around ball when armed, but Three.js gold glow (armed only) + edge glow (armed or flight) is normative. When neither armed nor in free flight, no gold glow is shown.
- **Stacking/limits & Auto-arm**: Only one free shot can be armed at a time (`isFreeShotActive` boolean, not counted). Multiple `freeShot` supply just allows multiple future free launches sequentially, **persisting automatically** after each free launch while supply remains. `freeShot` cannot be placed as a circle and does not participate in `canPlace`/drag/remove/area upgrades; it has no hotkey.

## 6. Supply (Inventory Limits)

- `supply = { amplify:number, nullify:number, flip:number, rotate:number, freeShot:number }` in `src/main.js` (or `src/supply.js`).
- Initialized to `{1,1,1,1,0}` on new game (`initLevel(0)`, `resetGameAfterWin`, `startNewGameFromMain`, `endRun`, `clearProgress`, page reload with no save). **New games start with `1` `rotate`** and `1` each other spatial (`amplify`/`nullify`/`flip`) and `0` `freeShot` (passive stock, shown in HUD as `(+0)`). Persists through death/`R` and through hole advances **minus win-consumption** for spatial types (see §7) and **minus launch-consumption** for `freeShot` (see §5.2).
- **Placement guard (spatial)**: `canPlace(type) => type!=='freeShot' && modifiers.filter(m=>m.type===type).length < supply[type]` (for `amplify`/`nullify`/`flip`/`rotate`). Place allowed iff true; otherwise rejected (no `modifiers` push, no `syncModifiersToField`). UI shows disabled slot / desaturated preview, tooltip `No supply remaining`. `freeShot` never uses `canPlace`.
- **No activation guard for freeShot via hotkey**: `freeShot` has **no hotkey**; toggling via `4` is disabled. `canActivateFreeShot()` may remain for auto-arm check (`supply.freeShot>0`) but is not bound to `4`. `updateHotbarUI()` shows for each **spatial** slot (`amplify`/`nullify`/`flip`/`rotate`) the current supply `supply[type]` on one line (`{icon} {Name} {supply}`) and disabled styling for those 4 slots; `freeShot` supply is shown in HUD (`Attempts Left: X (+Y)`), not in hotbar; collapsed hotbar hides spatial slots but still enforces guards.
- Dragging does not check/consume supply. Right-click removal of a spatial circle frees one spatial slot (does not affect `freeShot` or `rotate` beyond its type). `updateHotbarUI()` must be called after any `supply` or `isFreeShotActive` change and after resize.
- `addToSupply(type,n)` increments counter (used by rewards, see `09-rewards-and-progression.md`). For `freeShot`, `n` is `5` via `Free Shot Supply +5` reward; for `rotate`, `n` is `1` per reward.

## 7. Consumption on Win (REQ-035)

- When a hole is beaten (`WIN` → `handleNextHole`/`advanceHole` before clearing), iterate **snapshot** of `modifiers` (spatial only) and for each `m`: `supply[m.type]=Math.max(0, supply[m.type]-1)` (only `amplify`/`nullify`/`flip`/`rotate`). Clamped, exactly once per win (guard against double `handleNextHole`), not on death/manual removal/drag/`End Run`.
- `freeShot` is **not** consumed on win; it is only consumed on free launch per §5.2. If `isFreeShotActive` was armed but win occurs before launch, it remains armed into next hole until used or cleared.
- Then `modifiers=[]; syncModifiersToField(); updateHotbarUI(); saveProgress();` For non-final holes next hole's hotbar reflects reduced spatial supply (type that hit `0` becomes disabled until reward replenishes). For final hole `Course Completed!` → `clearProgress()` resets to `{1,1,1,1,0}` (consumption moot before reset).
